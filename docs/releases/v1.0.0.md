# v1.0.0 · g2rain-basis 首个稳定版

G2rain（谷雨）是面向企业的开源智能体平台，连接模型、知识与业务工具，以 SaaS 基座和应用开发工具链支撑智能应用落地。智能体平台已开源，具体组件、版本与接入方式以各责任仓库的说明为准。`g2rain-basis` 是其中负责组织、身份主数据、应用资源与权限关系的基础领域服务，不是整个平台、Gateway、IAM 或前端应用的替代品。它为 IAM、Gateway、管理端及其他平台服务提供这些领域能力；认证、入口校验、部署编排和环境安全仍由相应组件与运行环境共同保障。

## 交付、构建与镜像

- 项目版本：`1.0.0`；许可证：根目录 Apache License 2.0（`Copyright © 2025 g2rain.com`）。
- 构建要求：JDK 25、Maven 3.9+；运行要求：MySQL 8.0.13+、Redis、Nacos，以及启用审计事件时的 Kafka。
- 镜像：`ghcr.io/g2rain/g2rain-basis:1.0.0` 和 `ghcr.io/g2rain/g2rain-basis:sha-<完整提交 SHA>`；不更新 `latest`。
- API 制品：`com.g2rain:g2rain-basis-api:1.0.0`，连同根父 POM 发布到 `https://maven.pkg.github.com/g2rain/g2rain-basis`。镜像成功后自动调用 Maven 发布；Maven 失败不会回滚镜像，手动重复发布同一版本可能冲突。
- 镜像使用 Eclipse Temurin Java 25 JRE，Jib 从 Spring Boot 可执行 Jar 组装，入口为 `com.g2rain.basis.Application`，声明端口 `8080`；OCI source、title、version 与 `Apache-2.0` 标签指向本仓库。
- 本地验证和本地镜像：`mvn clean verify` 后运行 `./build.sh 1.0.0`。脚本会再次执行 Maven `clean install`（含现有测试），再以同一 Jib 配置构建到本地 Docker daemon。GitHub Actions 在 tag 提交上执行 `mvn clean install`，再于 Startup 目录以同一 Jib 配置直接推送镜像；成功后调用 API Maven 发布工作流。

## 发布顺序与 GHCR

1. 按 `feature/* → develop → main` 流程，将发布改动与本说明合入 `main`，并在该提交完成验证。
2. 在该 main 提交创建并推送 `v1.0.0`。工作流只接受精确的 `v<major>.<minor>.<patch>` 格式，会验证 tag 提交在 `main` 历史、Maven 版本一致且本文件非空。
3. 成功后确认 Actions 摘要同时列出版本标签与完整 SHA 标签；登录成功、构建成功或部分 layer 上传都不代表两个标签均已成功推送。
4. 首次成功推送后，在 GitHub 仓库 **Packages → g2rain-basis → Package settings → Change visibility → Public** 将包设为 Public。若组织管理员禁用修改，请联系组织管理员处理。
5. 已有包即使工作流声明 `packages: write`，仍可能需要在 **Package settings → Actions access** 授予 `g2rain/g2rain-basis` 写权限；遇到 GHCR `denied` 应优先检查此项与组织 Packages 策略。

公开后可匿名拉取指定版本：`docker pull ghcr.io/g2rain/g2rain-basis:1.0.0`。私有包需要使用具备 `read:packages` 权限的凭据登录。镜像发布本身不创建 GitHub Release、不部署服务，也不执行数据库迁移。

## 配置、安全与验证状态

运行时通过环境变量、Secret 或受控 Nacos 配置注入数据库、Redis、Kafka 和 Nacos 凭据；不要通过镜像、命令行或仓库提交传递生产密钥。Jib 最终镜像不包含仓库源文件、`codegen.properties` 或 Docker 构建上下文；但 Spring Boot Jar 会包含 `application.yml`、`application-dev.yml`、`application-nacos.yml`、`banner.txt` 与 `logback-spring.xml`。其中已跟踪的 `application.yml`、`application-dev.yml` 和 `application-nacos.yml` 含 Nacos、数据库等开发默认凭据；这些文件会随 JAR 进入镜像。维护者必须在首次公开推送前迁移或覆盖这些值，并在凭据曾被复用时轮换；Docker 忽略规则不能处理已打入 JAR 的配置。

工作流设计的自动验证范围是 Maven 编译、单元测试、打包和 Maven 生命周期；现有测试以 Service/领域工具单元测试为主，不证明真实 MySQL 约束、MyBatis 映射、数据隔离 AOP、Controller 访问控制、Kafka/Redis 交互、跨服务协作、容器启动、GHCR 推送、匿名拉取或实际部署。本地验证结果应在创建 tag 前单独记录；在线演示、容器构建、GHCR 推送、匿名拉取和部署验收是彼此独立的验证项，本发布准备不声称它们已完成。其余架构接入与安全限制见[架构差异与接入项](../architecture/deviations.md)。
